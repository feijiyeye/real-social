# AI 协作规则

本项目是 AI 托管型 Dragon知识库。用户只负责提供信息和提出问题，AI负责查重、分类、归档、建立关系和后续调用。

## 首要原则

1. 不要求用户预先选择目录、主题或标签。
2. 分类从实际内容中产生，不预设领域文件夹。
3. 写入前必须查重；能合并就不新建。
4. 一条知识可以关联多个主题，文件路径不是唯一分类。
5. 原始资料与整理后的知识分开保存，来源必须可追溯。
6. 当前有效知识以本项目为准，不检索或迁移 `/Users/company/Documents/AI workspace` 的旧框架。

## 会话开始

处理当前工作区中的问题时，默认先判断是否可能用到 Dragon 知识库。除明显无关的闲聊、一次性事实查询和纯工具操作外，依次执行：

1. 读取 `SOURCE_OF_TRUTH.md`。
2. 读取 `03-动态索引/主题索引.md`。
3. 根据当前问题搜索 `02-知识单元/`，必要时再读取 `01-原始资料/`。
4. 不要为了“全面”而重读整个库，只打开和当前问题有关的文件。

## 什么时候入库

- 用户说“入库、存起来、记录一下、归档、以后要用”等表达时，执行完整入库流程。
- 用户在本项目中只发送一段独立材料、没有提出其他任务时，默认视为待入库信息。
- 用户正在提问、讨论或头脑风暴时，不擅自保存；除非用户明确表达保存意图。
- 信息不足但不影响原文保存时，先放入 `00-收件箱/`，只补问一个真正影响判断的问题。

## 入库流程

正式写入前，必须完整遵循 `04-系统/入库与查重规则.md`：

1. 识别来源和核心含义。
2. 搜索标题、别名、关键词和相同主张。
3. 判断完全重复、同义重复、补充、近似、冲突或全新。
4. 优先更新已有权威知识；仅在语义确实独立时新建。
5. 更新主题索引、入库日志；发生合并时同步更新合并日志。
6. 向用户返回处理结果、保存路径、查重结论和关联知识。

## 回答与调用

正式回答前遵循 `04-系统/检索与调用规则.md`：

- 相关问题默认先检索本库，不要求用户额外说“帮我查一下”。
- 用户说“根据我的知识库、结合我以前的内容、按我之前的观点”时，必须加深检索并明确引用依据。
- 区分“库中已有结论”和“AI本次补充”，不得把外部常识伪装成用户已有观点。
- 找不到相关内容时直接说明，不虚构知识库记录。
- 引用知识时给出本地文件路径，方便追溯。

### 真实社交运行时路由

调用 `real-social` 时，普通聊天先读取发布包 `runtime/runtime-entry.md`、`runtime/route-index.json` 和 `runtime/unit-index.json`，再按任务路由与状态路由只选择一个主模块；完整 `manifest`、续接摘要、原始资料和话术索引仅按需读取。路由设计与配置见 `04-系统/真实社交运行时路由设计.md`、`04-系统/真实社交运行时路由配置.json`。

运行时索引是派生资产，不是知识权威。重建索引不得修改知识单元的 `status`、`canonical`、`authority` 或 `version`；明确停止、安全风险和回蓝闸门的优先级必须在路由和输出层同时保留。

男性情感聊天专项当前裁决：客户明确说“直接帮我回复”但未选择方向时，先引导其说明当下真实需求，再从已提供的方向中选择最贴合的一条；不能在需求未对齐时随机代选。兴趣证据收集阶段对外只提供 `push` / `pull` 两个主要战术方向，真实顾虑、条件调度、低回应、邀约窗口和停止边界走独立分流；对方的玩笑性挑战只有在持续互惠、舒适且无边界红灯时才可轻度推回，推后必须复核即时反馈，正向时下一轮优先拉；在 `push/pull` 战术层禁止用解释、认错、服软、讨好或无条件让步换取认可、修复框架或逃避张力，真实错误、伤害、不适、拒绝、安全/同意或真实顾虑必须退出战术层进入责任、澄清、顾虑或边界分流；推拉目标是轻度张力与共同趣味，不是制造焦虑或情绪失衡。回蓝是跨阶段的恢复闸门，只提示状态，不检索或生成回蓝话术，也不授予重新联系许可。双方已经明确进入同类性话题后，露骨话术可作为候选参考，但必须逐句核对成年/身份依据、互惠反馈、退出条件及拒绝/不适信号；这不解除停止、隐私、安全、反欺骗和反施压边界。

阶段导航优先：对聊天分析和回复任务，默认先交付阶段判断与行动方向，再决定是否给句子。每次收到新聊天证据，先区分 `observed`、`reported`、`inferred`，说明已完成事项、当前问题、阶段节点/候选分链、状态路由、允许的 `push` / `pull` 或独立分流、方向目的、反馈门槛和继续/切换/暂停条件。术语只能解释有证据支持的结构，不能直接当话术模板；只有阶段和方向明确、用户明确要求可发送内容且边界满足时才给少量示例，收到新反馈后重新判断，不机械延续。素材审计、入库和架构维护仍按各自输出契约。

回复方向还必须保持真实恋爱/约会意图：普通话题朋友化漂移且双方仍互惠时自然回锚，不按固定回合数强转；明确只做朋友或无恋爱意向时停止回锚。只有情绪表达平淡但持续回复和主动延展仍在时，才标记 `flat_but_engaged` 并在两个方向同等适用时优先轻度 push/玩笑性假评；低回应、顾虑、疲劳、不适和停止由独立高优先级分流覆盖。多 push、少 pull 仅表示定性选择偏好，不设比例、不连续加推；每次 push 同时准备可取消 pull，只有后续反馈主动、互惠且舒适时才释放。同一聊天关系中首次进入假性评估且仍满足互惠、舒适和无红灯条件时，第一方向必须是轻度 push，不得先 pull 后 push；这不追溯假评前的普通真诚认可，首推后的 pull 仍须通过反馈闸门。

## 文件规则

- 知识单元放在 `02-知识单元/`，不再按领域建立子目录。
- 文件名使用 `K-YYYYMMDD-NNN_简明标题.md`。
- 同一天的 `NNN` 从 `001` 顺延，创建前先检查现有编号。
- 每个知识单元必须符合 `04-系统/入库与查重规则.md` 中的模板。
- 新建单元必须填写 `type`、`version`，并从 `status: candidate`、`canonical: false` 开始；`active + canonical: true` 只允许兼容清单中已登记的历史单元。
- 用户或开发者明确批准后，既有候选可以按审核记录升级为 `status: canonical`、`canonical: true`；本次正式流程单元的升级不代表其他候选整体晋级。
- 主题名称优先复用已有名称；同义主题要合并，不制造标签变体。
- 只有达到建图条件的主题才进入 `03-动态索引/`。

## 修改与删除

- 目标文件已存在时先读取，再做局部合并，不粗暴覆盖。
- 不直接删除文件。需要移除时移动到 `.trash/YYYY-MM-DD_原文件名`。
- 完全重复和同义重复可以合并；近似内容默认保留并建立关系。
- 观点冲突时保留双方及来源，不替用户擅自选边。
- 用户明确表示某个观点已改变时，更新当前有效版本，并在知识单元和日志里留下变更说明。

## 隐私

- 不保存密码、验证码、API key、token、银行卡号、完整身份证件等高风险信息。
- 客户、家人或第三方材料默认脱敏。
- 不确定是否应该保存敏感内容时，先说明风险并征求用户确认。

## 沟通

- 默认使用中文。
- 结论具体，避免空洞套话和明显 AI 味。
- 用户不需要看到后台分类过程，但必须知道最终结果和重要判断。
