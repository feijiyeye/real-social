# 真实社交运行时路由设计

## 目的

本设计把 `dbs` 的“任务前路由、任务后导航、按需进入叶子模块”改造成 `real-social` 的内部运行时机制。目标是减少每次调用时重复读取的大型治理文件、完整话术索引和全部案例，同时保持证据核对、候选状态和安全边界不变。

这是运行时组织方式，不是新的聊天理论，也不改变任何知识单元的 `status`、`canonical` 或结论。机器配置见同目录的 `真实社交运行时路由配置.json`。

## 两级路由

每次调用先识别任务，再识别聊天状态：

```text
用户输入
  -> 任务模式识别
     first_use | analyze_chat | reply_request | case_lookup
     source_audit | ingest_material | architecture_maintenance
  -> 硬边界与状态识别
     stop_boundary
     privacy_safety_age_consent
     recovery
     clarify
     concern_condition
     low_response
     invite
     interest_push_pull
     unknown_stage
  -> 只选一个 primary_module
  -> 最多携带两个 auxiliary_modules
  -> 读取该模块的正式单元和小型索引
  -> 必要时再检索案例或话术
  -> 输出结果、状态字段和下一步导航
```

任务路由决定“要完成什么”；状态路由决定“当前先处理什么”。状态路由优先级高于一般任务意图，例如一条同时包含“帮我回复”和“不要再联系”的消息，主模块必须是 `stop_boundary`，不能进入推拉或话术生成。

## 路由优先级

```text
100  stop_boundary
 90  privacy_safety_age_consent
 80  recovery
 75  clarify
 70  concern_condition
 60  low_response
 50  invite
 40  interest_push_pull
  0  unknown_stage
```

路由命中不是事实判定。关键词只提供候选入口；模型仍需回到最近完整聊天，区分 `observed`、`reported`、`inferred`，并在证据不足时输出 `unknown_stage`。

## 阶段导航优先交付

阶段导航是聊天分析和回复任务的默认输出契约，不是新的状态路由。收到新聊天证据后，模型先分离 `observed`、`reported`、`inferred`，再输出已完成事项、当前问题、阶段节点与候选分链、适用 `state_route`、允许的 `push` / `pull` 或独立分流、方向目的、反馈门槛以及继续/切换/暂停条件。阶段术语只能解释有证据支持的结构和转移条件，不能直接当作话术模板。只有阶段与方向明确、用户明确要求可发送内容且边界条件满足时，才进入少量示例；新反馈到达后必须重新计算阶段、方向和反馈门控，取消失效预案，不机械沿用上一条建议。素材审计、入库和架构维护仍遵循各自的任务输出。

该原则通过配置中的 `stage_navigation` 元数据随运行时索引发布，供模型和校验脚本读取；它不改变状态优先级、候选单元的 `status` / `canonical`，也不新增 `push` / `pull` 以外的战术方向。

## 模块职责

### 任务模块

- `first_use`：只在首次使用或用户明确询问入口时加载，完成后回到当前真实任务。
- `analyze_chat`：阶段、分链、证据、反证和风险检查；默认不读取话术全文。
- `reply_request`：只有完成需求对齐、方向选择和边界核对后，才调用候选话术并生成少量示例。
- `case_lookup`：从 `unit-index` 筛选相似案例；候选案例必须标出来源性质和结果状态。
- `source_audit`：允许读取完整 `manifest` 和原始来源，回答可追溯性问题。
- `ingest_material`：读取入库与查重规则，写入前查重，保持候选状态。
- `architecture_maintenance`：读取本设计、配置、构建/校验脚本和完整状态文件，处理维护问题。

### 状态模块

- `stop_boundary`：明确拒绝、删除、停止或“不要再联系”优先；不把拒绝重解释为测试，不自动重启。
- `privacy_safety_age_consent`：先核对隐私、安全、成年/身份、同意与退出条件；未核实前不进入高风险话术。
- `recovery`：命中客户自身耗竭、冲动加码或持续无效投入时，只返回“可以回蓝”及暂停条件；`phrase_retrieval=disabled`。
- `clarify`：处理事实错误、误会、实际伤害或需要承担责任的说明；退出 `push/pull` 战术层后，才可进行简洁、如实的澄清、道歉或修复，不把这些动作当作推拉。
- `concern_condition`：承接真实顾虑、现实限制和邀约条件；不把忙碌、生病、交通、时区或改期直接解释成兴趣信号。
- `low_response`：处理低回应、暂停、减少投入和是否有新证据；不使用惩罚式消失或固定等待重启。
- `invite`：判断是否存在直接邀约窗口，并核对双方意愿、时间、地点、方便和安全；终点是“双向兴趣与可执行见面”。
- `interest_push_pull`：仅在兴趣证据收集阶段对外展示 `push` 或 `pull`。这两个方向不是所有情形的强制二选一。
- `unknown_stage`：信息不足、互斥信号未裁决或输入只给一句孤立文本时，暂停战术判断并只追问关键变量。

### 推拉组合状态机

`interest_push_pull` 路由只提供战术入口，不替模型完成事实判断。进入组合逻辑前，先把对方的“推”分成三类：

先执行五项正式选择规则：

1. `romantic_intent_anchor`：普通话题发生朋友化漂移且双方仍互惠时，自然回锚吸引、关系判断或约会方向，不按固定回合数强转；明确只做朋友或无恋爱意向时停止回锚并进入澄清/边界分流。
2. `affect_engagement_policy`：只有情绪表达相对平淡且持续回复、主动提问或延展仍在时，才标记 `flat_but_engaged`；连续低回应、顾虑、疲劳、不适和停止不是“没有情绪”。
3. `direction_bias`：在 `flat_but_engaged` 且 push/pull 同等适用时偏向低强度 push 或玩笑性假评；该偏好不产生固定比例或连续加推配额。
4. `planned_pull`：每次 push 同时准备可取消的 pull 预案。反馈前保持 `pending_feedback`；只有积极、互惠、舒适三项证据同时成立时为 `ready`，笼统正向但证据不全仍等待；反馈不明、变淡、转负或命中更高优先级状态时为 `blocked`。`tactical_direction` 只记录实际允许的下一方向，不能与 `pending_feedback` / `blocked` 同时回显 push。
5. `initial_false_evaluation_order`：当 `false_evaluation_stage=first`、当前仍适用 `interest_push_pull`、双方互惠舒适且无边界红灯时，首次假评组合固定为 `push_then_feedback_gated_pull`，禁止 `pull_then_push`。若首个 push 尚未发出，即使请求 pull，实际方向仍为 push；若 push 不适用则不启动假评。首推已经发出时转交既有 `planned_pull` 状态机，不能再次强制 push。假评前的普通真诚认可、礼貌回应或非假评连接不受该顺序约束。

1. **玩笑性挑战或轻度反驳**：对方仍自愿参与、继续提问或延展，并且没有边界、舒适度或安全红灯；此时才允许轻度、对等但不必同强度地 `push` 回应。
2. **真实顾虑、条件限制、低回应或安全信号**：不得推回，分别转入 `concern_condition`、`low_response` 或安全分流。
3. **明确拒绝、停止、删除或不要再联系**：直接转入 `stop_boundary`，不得把它解释成测试或需要突破。

允许推回时，“维持框架”只表示保持自己的真实偏好、边界和节奏，不表示压过、控制或迫使对方。每次 `push` 后都必须记录即时反馈检查：若对方继续主动、接住互动且舒适，下一轮优先 `pull` 以认可、连接、降低距离或留出空间；若反馈不明、变淡、回避或转负，停止追加 `push`，按证据改用 `pull`、澄清、暂停或边界分流。

`push` 的可接受目的只有轻度张力、真实立场表达和获取新的可观察反馈。推拉节奏以共同趣味、舒适和可退出为验收标准，禁止把焦虑、嫉妒、羞耻、不安全感、情绪失衡或“情绪过山车”当作目标、指标或固定脚本。

#### 战术层禁止动作与责任例外

在 `push/pull` 战术层，不得把过度解释、辩解式说明、策略性认错、讨好式道歉、服软或为换回兴趣而放弃真实边界当作回复动作。这里禁止的是以这些动作换取认可、修复框架或逃避张力的战术用途，不是禁止承担真实责任。

如果确有事实错误、实际伤害、对方不适或拒绝、安全/隐私/成年/同意问题，或对方提出需要认真处理的真实顾虑，必须退出 `interest_push_pull`，转入 `clarify`、`concern_condition`、`privacy_safety_age_consent` 或 `stop_boundary` 等分流。必要时可以并且应当简洁、如实地澄清、道歉、修复或调整；这些动作不计为 `push/pull`，也不自动恢复旧战术方向或重新联系许可。物流协商中的合理调整和尊重边界不等于“服软”。

## 懒加载契约

普通聊天首轮只读取：

1. `runtime/runtime-entry.md`；
2. `runtime/route-index.json`；
3. `runtime/unit-index.json`；
4. 正式流程单元 `K-20260826-001`。

以下内容默认延后：

- 完整 `knowledge/manifest.json`：仅构建、校验、来源审计时使用；
- 续接摘要和历史架构：仅维护、入库或恢复上下文时使用；
- 2867 条完整话术索引：只有在方向已确定且满足示例门槛后，按路由查询；
- 原始资料、外部来源和归档：只回读与命中条目对应的小范围上下文；
- `_original_dragon_root/` 与 `archive/`：不纳入默认搜索。

小型索引只保存元数据、路径、路由和稳定键，不复制长篇正文。它们是派生索引，可从 Dragon 主库重新生成，不是新的知识权威。

## 话术路由

话术召回采用“候选入口 -> 路由分片 -> 原文回读”三步：

1. 先从 Jackson 41 条人工候选和 Apple Notes 代表性候选中找路由入口；
2. 命中后按 `route_id`、阶段、方向、说话人和调用状态缩小范围；
3. 再回读原始 Markdown、稳定文本、SRT 或外部原件的相邻上下文，并经过 `K-20260823-053` 的边界过滤。

`recovery` 路由不执行第三步。亲密/性话题路由只有在双方明确进入同类话题、成年/身份依据充分、存在持续互惠反馈且没有拒绝或不适时才解除露骨内容的隔离；其他风险仍然逐句过滤。

运行脚本保留的 `--sexual-context` 只是上游兼容标记，不能替代四项显式核对（同类话题、成年/身份依据、互惠反馈、无拒绝或不适）。四项条件未同时满足时，亲密话题路由继续阻断检索。

## 任务后导航

导航只给出当前最值得处理的一个后续方向，不预设长链。典型关系如下：

- 分析完成且用户明确需要示例：`analyze_chat -> reply_request`；
- 新反馈出现低回应或顾虑：优先转 `low_response` 或 `concern_condition`；
- 满足双方兴趣和可执行条件：`invite -> conversation_complete`；
- 邀约条件未齐或未成功：回到 `analyze_chat`，重新依据新证据判断；
- 回蓝后只有新的自愿、可观察互动才回到 `analyze_chat`，不按固定天数自动重启。

## 验收标准

- 普通聊天不要求先读取完整 `manifest`、续接摘要或完整话术索引；
- 每次只返回一个主路由，辅助路由不超过两个；
- 明确停止、安全风险和回蓝命中时，机器结果能阻断不应发生的召回；
- 推拉路由能输出 `push_back_eligible`、`post_push_check`、`pull_after_push`、`push_purpose`、`romantic_intent_anchor`、`romantic_reanchor_permitted`、`affect_engagement_policy`、`comfort_state`、`flat_but_engaged`、`direction_bias`、`false_evaluation_stage`、`initial_false_evaluation_order`、`initial_false_evaluation_status`、`planned_pull`、`tactical_action_constraints` 和 `roller_coaster_goal` 字段，并保留责任与边界例外分流；
- `K-20260826-001` 保持唯一当前正式线上流程，47 个男性情感候选的 `candidate`/`canonical: false` 状态不变；
- 构建、校验和回归测试能够从 Dragon 主库重建所有运行时索引；
- 安装目录与发布包的哈希校验一致。
